## 2. Technical Blog Post Draft (Dev.to / Medium / Hashnode) — Bonus Blog Track
**Title**: *Taming Haunted Codebases: How We Built NecroSpec Studio with Kiro's Spec-Driven Development for Kiroween 2026*

> *Disclaimer: This blog post was created for the purposes of entering the Kiroween 2026 Hackathon hosted by Kiro on Devpost.*

### Why Vibe-Coding Breaks Down at Scale
When building complex applications with AI, jumping straight from a one-line prompt to code generation often produces fragile architecture and hidden regressions. While preparing for the **Kiroween 2026 Hackathon**, we wanted to build a reusable **Skeleton Crew** starter template that makes Kiro's best practices—**Specs**, **Steering**, **Hooks**, and **Property-Based Testing (PBT)**—visual, testable, and effortless to adopt.

### Inside Our `/.kiro` Architecture
1. **Steering (`.kiro/steering/`)**: We defined `product.md`, `tech.md`, `structure.md`, and `AGENTS.md` with `inclusion: always` so Kiro continuously enforces zero-backend portability and accessibility standards.
2. **EARS Specifications (`.kiro/specs/necrospec-core/`)**: Using the Easy Approach to Requirements Syntax (`WHEN <trigger> THE SYSTEM SHALL <response>`), we eliminated ambiguous edge cases before writing UI code.
3. **Automated Verification Hooks (`.kiro/hooks/test-on-save.json`)**: Every file save triggers our 100-case Property-Based Testing suite (`tests/pbt_spec_invariants.test.js`), proving that our EARS compiler is both complete and idempotent.
